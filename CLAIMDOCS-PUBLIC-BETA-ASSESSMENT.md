# ClaimDocs public-beta assessment

Decision: **`INCLUDE_AFTER_BOUNDED_REPAIR`**.

This recommends ClaimDocs as a *conditional future generic beta substrate*. It does not include it in the frozen Constellation candidate, authorize implementation or promotion, replace Cartography, or establish beta acceptance. The working claim-documentation engine earns further investment; a working obligation ledger does not already exist. If the [single bounded slice](CLAIMDOCS-BETA-SLICE.md) cannot meet its acceptance criteria without a service/control plane, keep the components separate and revisit this decision.

## What it solves, and what it does not

ClaimDocs was designed to prevent diagrams/prose from silently becoming stronger than their declared evidence. It already has portable per-project vocabulary, typed graph relations, cited bases, Python cited-body checks, independent recorded human adequacy and mode-preserving readout. That generic separation is worth preserving:

`resolved ≠ supported; cited-fresh ≠ closure-fresh; closure-fresh ≠ adequate; rendered ≠ true`

It is not an observation store, evaluator, notification dispatcher, operational authority, executor, incident manager or work scheduler. It does not currently answer all nine public-beta questions. In particular, complete outstanding obligations, explicit lifecycle, forcing relevance and semantic closure are new work. This is a useful implemented foundation, not a forgotten mostly complete registry.

## Concrete forcing cases

| Case | Existing useful foundation | Missing composition |
|---|---|---|
| Labelwatch retention | Separate evidence-backed relations for manual maintenance, scheduled failure, portfolio architecture and application adoption | Durable successor identity, owner/tracker, complete enrolled inventory, forcing review and evidence-backed closure |
| Operator legibility | Explicit relations and non-claims can distinguish stale monitoring, unknown dependent state and service failure | Qualified domain context and current presentation contracts; ClaimDocs must not become the evaluator or invent recovery |
| Constellation acceptance | Exact-generation receipts and distinct modes can describe bounded standing | Current selection/supersession, immutable historical context, acceptance scope and residual obligations |

The October 5 retention failure is a forcing case for reviewing deferred historical-storage debt. It is not by itself proof that a particular direct-DuckDB migration gate has been met. Labelwatch already has qualified Parquet/archive/catalog slices; an incomplete longer-term transition must not erase them. Service recovery, incident closure and corrective-action closure are separate. Specific migration admission remains with the existing application owner and tracker.

The accepted Workbench reveal did not exercise Linear Accountant; separately accepted remediation v2 did. Subsequent optional read-only Workbench composition strengthens a narrow visibility claim without rewriting the reveal, enabling model mode by default or granting effects. This is a representative partial-acceptance/successor case, not permission to import private campaign machinery into public runtime.

## Authority and ownership boundaries

| Responsibility | Owner |
|---|---|
| Context recall/synthesized reasoning | Continuity/cache and agent working set; incomplete retrieval cannot establish obligations |
| Authored claim/obligation semantics and closure contract | Owner-reviewed portable corpus, potentially validated/projected by ClaimDocs |
| Execution owner, priority, scheduling and workflow status | External issue/project tracker |
| Runtime evidence/currentness and forcing-condition observations | Existing Constellation observation/support/evaluator paths |
| Effects, custody and recovery | Existing AG/Docket and independent postcondition; ClaimDocs cannot grant them |
| Cross-program doctrine, ownership map and project-specific history | Cartography, as one corpus/policy instance, not a prerequisite for public users |

Prefer a **one-way dated read-only tracker projection** bound to an authoritative work-item reference. Owner-authored semantic obligations retain why/evidence/closure; imported execution status retains provenance and age. A closed tracker item without closure evidence is a visible mismatch, not `SATISFIED`. No bidirectional synchronization, assignments, priority edits or tracker credentials inside the portable corpus are required.

Cartography's generic claim/basis/gap/successor relationships are candidates for reusable validation. Its Constellation doctrine, component ownership, release policy and historical maps stay project-specific. Manual archaeology and private completion/acceptance conventions are migration inputs, not a public onboarding requirement. No Cartography rewrite or automatic corpus conversion is proposed.

Continuity remains useful for reconstruction, including its separately governed memory/custody interfaces. Context retrieval is cache-like for this job. Correctness must not depend on remembering to ask it. Scoped enumeration and process hooks must be deterministic, mandatory for their enrolled workflow and visibly incomplete when coverage is unavailable.

## Minimum public shape and integration contract

Favor authored files + versioned schemas + CLI/library + deterministic portable reports. No daemon, database service, model, new UI, automatic tracker mutation or remediation is needed for the first slice. The source-free consumer should inspect evidence attachments and explicit current/historical/unknown labels without a checkout or private corpus. Rechecking a code-symbol basis can separately require its declared source snapshot; that limitation must not masquerade as complete verification.

Proposed read-only flows, **not implemented**:

- Lane startup: explicit affected scope → complete enrolled unresolved inventory/current claims → operator context, with coverage receipt.
- Incident diagnosis: observation evidence → scoped claims and matching review conditions; unknown matches remain unknown.
- RCA closure: immediate recovery evidence → preserved incident claims + successor dispositions and external references.
- Deployment: changed prerequisite evidence → relevant blocked/deferred review, not execution authority.
- Acceptance: exact scoped receipt → strengthened/superseding claim and separately justified obligation disposition.

In the proposed slice, ClaimDocs would represent forcing predicates and validate referenced evidence identities and declared interpretation scope. Existing Constellation evaluates runtime conditions; the first offline slice may only validate an explicit owner-supplied match/nonmatch/unknown witness. It must not invent a general temporal rule engine. A forcing match marks **review due**, not automatic work dispatch or satisfaction.

## Negative evaluation

Eleven required boundary cases were reconciled against actual source with nineteen isolated CLI checks. One passes existing scope (generic operation without Cartography); three are partial (missing-basis refusal, cited-body/date staleness, fixed-input rendering); seven have no implementation (identity conflict/strength ordering, outstanding-obligation visibility, tracker closure, supersession, durable branch-independent state, automatic non-Continuity projection and forcing evaluation). No unsupported case is counted as a pass.

Newer weaker duplicate evidence can shadow older basis records by filename; duplicate edges and ignored supersession are real blockers to trustworthy current state. Rendering can bypass separate basis/adequacy verification; the report/UI must identify what was actually checked. Admission SHA labels are not source-revision attestation. Historical output reproducibility does not currently guarantee a historical label or retained basis custody. These require the bounded gate, not stronger marketing.

## Formalization consideration

Proposed durable invariant: within an explicit enrolled inventory and evidence snapshot, neither recency, cache omission nor tracker closure discharges an unresolved obligation; terminal semantic disposition requires evidence or attributable supersession/retirement. Scope excludes unknown unenrolled promises and assumes owner/custody identity. Existing tests establish only current command limits. Before implementation acceptance, use a small state/enumeration model and shared vectors for coverage gaps, duplicate identities, closed-without-proof, supersession, review forcing and immutable history. The spike's integration owner makes this conditional architectural recommendation; implementation/acceptance needs a separately admitted lane. No percentages or whole-program maturity claim is warranted.
